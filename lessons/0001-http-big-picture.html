큰 그림: React와 ASP.NET Core는 HTTP로 대화한다

이번 수업의 목표는 하나예요. HTTP 요청 하나를 보고, 프론트엔드의 어느 코드가 그 요청을 보내고 백엔드의 어느 코드가 그 요청을 받는지 짚을 수 있게 되는 것.

태블릿 OK 약 15분 · 읽기 7분, 퀴즈 8분

왜 이것부터 배우나요?

앞으로 만들 앱은 서로 다른 두 프로그램이에요. 하나는 브라우저에서 돌아가는 React 앱(프론트엔드)이고, 다른 하나는 서버에서 돌아가는 ASP.NET Core API(백엔드)예요. 두 프로그램은 언어도(TypeScript, C#) 실행 위치도 다르고, 오직 HTTP 메시지로만 대화해요.

그래서 HTTP는 두 세계를 잇는 계약서예요. 실무에서 "버튼을 눌렀는데 저장이 안 돼요" 같은 버그를 만나면, 가장 먼저 확인하는 것도 "어떤 요청이 나갔고 어떤 응답이 돌아왔나?"예요. 설계도 마찬가지로, API를 설계한다는 건 결국 이 요청과 응답의 모양을 정하는 일이에요.

요청과 응답에 들어 있는 것

MDN 기준으로, 요청(request)에는 다음이 들어 있어요.[1]

  1. 메서드(method): 무엇을 하고 싶은지 나타내는 동사. GET은 조회, POST는 생성, PUT은 전체 수정, DELETE는 삭제예요.
  2. 경로(path): 대상 리소스. 예: /todoitems/1
  3. HTTP 버전
  4. 헤더(headers): 부가 정보. 예: 본문이 JSON이라고 알려 주는 Content-Type
  5. 본문(body): 보낼 데이터. POST처럼 필요한 메서드에서만 들어가요.

응답(response)에는 HTTP 버전, 상태 코드(status code)와 상태 메시지, 헤더, 그리고 필요할 때 본문이 들어 있어요.[1] "할 일 추가"를 예로 들면 실제 메시지는 이렇게 생겼어요.

① 요청: 브라우저 → 서버POST /todoitems HTTP/1.1
Host: localhost:7183
Content-Type: application/json

{"name":"우유 사기","isComplete":false}
② 응답: 서버 → 브라우저HTTP/1.1 201 Created
Location: /todoitems/1
Content-Type: application/json; charset=utf-8

{"id":1,"name":"우유 사기","isComplete":false}

같은 대화를 양쪽 코드에서 보기

아직 문법을 몰라도 괜찮아요. 강조된 부분이 위 메시지의 어느 부분과 짝인지만 찾아보세요.

프론트엔드 · TypeScript: 요청을 보내는 쪽const res = await fetch("/todoitems", {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify({ name: "우유 사기", isComplete: false }),
});
백엔드 · C# (ASP.NET Core Minimal API): 요청을 받는 쪽app.MapPost("/todoitems", async (Todo todo, TodoDb db) =>
{
    db.Todos.Add(todo);
    await db.SaveChangesAsync();
    return Results.Created($"/todoitems/{todo.Id}", todo);
});

백엔드 코드는 Microsoft 공식 튜토리얼에서 가져왔어요.[3] 짝을 정리하면 이렇습니다.

  • method: "POST" + "/todoitems" → 서버에서 MapPost("/todoitems", …)가 이 요청을 받아요. 메서드와 경로를 보고 처리할 코드를 고르는 걸 라우팅(routing)이라고 해요.[4]
  • body의 JSON → 서버에서 Todo todo 매개변수로 들어와요.
  • Results.Created(...) → 응답의 201 Created와 Location 헤더가 돼요.

개발 중 주소에 대한 메모. 프론트엔드 코드에 "/todoitems"만 적어도 되는 이유가 있어요. 공식 React + ASP.NET Core 템플릿은 Vite 개발 서버의 프록시(proxy)가 이 요청을 백엔드 주소(예: https://localhost:7183)로 넘겨 주도록 설정되어 있거든요.[5] 자세한 내용은 두 프로젝트를 연결하는 수업에서 다룰게요.

상태 코드: 응답의 첫 줄만 봐도 아는 것

상태 코드는 다섯 그룹으로 나뉘어요: 1xx 정보, 2xx 성공, 3xx 리다이렉트, 4xx 클라이언트 잘못, 5xx 서버 잘못.[2] API를 만들 때 자주 쓰는 코드는 이것들이에요.

코드뜻 (MDN 요약)이럴 때
200 OK요청 성공목록·단건 조회 성공
201 Created성공했고 새 리소스가 생김POST로 생성 성공
204 No Content성공, 보낼 본문 없음수정·삭제 성공[3]
400 Bad Request클라이언트 요청이 잘못됨필수 값 누락, 형식 오류
401 Unauthorized의미상 "인증 안 됨"로그인하지 않음
403 Forbidden누군지는 알지만 권한 없음남의 데이터 접근
404 Not Found리소스를 찾을 수 없음없는 id 조회
500 Internal Server Error서버가 처리 방법을 모름처리 안 된 예외

401과 403의 차이는 실무에서 자주 헷갈려요. MDN은 이렇게 구분해요. 401은 "unauthorized"라는 이름과 달리 실제 의미는 unauthenticated(누군지 모름)이고, 403은 "서버가 클라이언트가 누군지 알지만" 접근 권한이 없는 경우예요.[2]

마지막 한 가지: HTTP는 무상태(stateless)

MDN에 따르면 "같은 연결에서 연달아 보낸 두 요청 사이에도 아무 연결 고리가 없어요".[1] 서버는 직전 요청을 기억하지 않아요. 그래서 로그인 상태처럼 요청을 넘어서 유지해야 하는 정보는 쿠키나 토큰에 담아 매 요청마다 다시 보내야 해요. 나중에 인증 수업에서 이 사실이 다시 등장해요.

떠올리기 연습

위로 스크롤하지 말고 먼저 머릿속으로 답한 뒤에 펼쳐 보세요. 답을 떠올리려고 애쓰는 과정 자체가 장기 기억을 만들어요.

HTTP 요청에 들어가는 다섯 가지는?메서드, 경로, HTTP 버전, 헤더, (필요할 때) 본문.
4xx와 5xx는 각각 누구의 잘못인가요?4xx는 클라이언트(요청이 잘못됨), 5xx는 서버(서버가 처리하지 못함).
fetch("/todoitems", { method: "POST" })를 받는 C# 코드는 어떤 모양일까요?app.MapPost("/todoitems", ...): 메서드는 Map 뒤의 이름(Post)과, 경로는 첫 번째 인자와 짝을 이뤄요.

퀴즈

문항마다 기회는 한 번이에요. 틀려도 괜찮아요. 해설을 읽는 순간이 가장 많이 배우는 순간이에요.

React 화면에서 "할 일 추가" 버튼을 눌렀어요. 새 할 일을 서버에 보낼 때 가장 알맞은 메서드는?

새 리소스를 생성할 때는 POST를 써요. PUT은 이미 있는 리소스를 통째로 교체할 때 써요.[3]

POST /todoitems가 성공해서 새 할 일이 만들어졌어요. 가장 알맞은 응답 상태 코드는?

201 Created는 "요청이 성공했고 새 리소스가 생겼다"는 뜻이에요. 보통 POST 다음에 돌려줘요.[2] 200도 틀린 건 아니지만 정보가 덜 정확해요.

GET /todoitems/42를 보냈는데 42번 할 일이 DB에 없어요. 알맞은 응답은?

MDN은 404를 이렇게 설명해요. API에서는 "엔드포인트 자체는 맞지만 리소스가 존재하지 않는" 경우에도 쓴다고요.[2] 요청 형식에는 문제가 없으니 400이 아니에요.

GET /todoitems/7 요청을 받아서 처리하는 백엔드 코드는?

메서드(GET → MapGet)와 경로 모양(/todoitems/7 → /todoitems/{id})이 둘 다 맞아야 해요. {id} 자리에 7이 들어가요.[3]

로그인하지 않은 사용자가 "내 할 일 목록"을 요청했어요. 알맞은 응답은?

401은 의미상 "인증되지 않음", 즉 누군지 모른다는 뜻이에요. 403은 누군지는 알지만 권한이 없을 때 써요.[2]

다음 중 HTTP 요청에는 들어 있지 않은 것은?

상태 코드는 응답에만 있어요. 서버가 "결과가 어땠는지" 알려 주는 값이니까요.[1]

"HTTP는 무상태(stateless)다"의 뜻으로 가장 알맞은 것은?

연달아 보낸 두 요청 사이에도 연결 고리가 없다는 뜻이에요.[1] DB에 저장하는 건 당연히 가능해요. 무상태라는 말은 프로토콜에 대한 이야기예요.

HTTP 대화를 먼저 시작하는 쪽은?

MDN에 따르면 요청을 시작하는 쪽은 "항상" 브라우저(클라이언트)이고 서버는 절대 먼저 시작하지 않아요.[1] 서버가 먼저 알림을 보내야 할 때는 WebSocket 같은 다른 기술을 써요. 이건 나중에 다뤄요.
