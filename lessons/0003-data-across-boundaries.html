경계를 넘는 데이터: C# 객체가 JSON이 되어 TS에 도착하기까지

이번 수업의 목표: C# 클래스와 직렬화 설정을 보고 실제로 나갈 JSON을 정확히 예측하고, 그에 맞는 TS 타입을 쓸 수 있게 되는 것. 그리고 반대 방향으로 들어오는 JSON이 무엇을 검사받지 않고 통과하는지 알게 되는 것.

태블릿 OK 읽기와 퀴즈 약 25분 · PC 숙제 약 40분

시작 전 떠올리기 (지난 수업 복습). 답을 머릿속으로 먼저 말해 본 다음 펼쳐 보세요.

record class는 참조 타입인가요, 값 타입인가요? 그리고 동등성은 무엇을 기준으로 하나요?참조 타입이에요. 그런데 동등성은 값 기준이에요. 두 질문은 서로 다른 축이에요.
그럼 EF Core 엔티티로 record class가 맞지 않는 이유를 한 문장으로?EF Core는 키 하나에 인스턴스 하나를 두고 참조 동등성으로 추적하는데, record는 동등성을 값 기준으로 바꾸고 with 복사본 방식을 권하기 때문이에요. 그래서 "같은 엔티티"의 기준이 둘로 갈라져요.[12]

경계 질문: 이런 정보를 찾는 방법

지난 숙제에서 "enum을 JSON으로 바꾸는 attribute 같은 정보는 어떻게 공부해야 할지 모르겠다"는 질문이 있었어요. 답은 경계(boundary)라는 개념이에요. 데이터가 한 세계에서 다른 세계로 넘어가는 지점을 말해요.

  • C# 객체 → JSON 텍스트 → TS 객체 (API 응답)
  • TS 객체 → JSON 텍스트 → C# 객체 (API 요청)
  • C# 객체 → DB 행 (EF Core, 나중 수업)

각 세계는 타입 체계가 달라요. C#에는 enum, Guid, DateTimeOffset이 있지만, JSON에는 문자열, 숫자, 불리언, null, 객체, 배열밖에 없어요. 그래서 경계를 넘을 때마다 누군가 변환 규칙을 정해야 하고, 버그는 거의 언제나 그 규칙을 모르는 곳에서 생겨요. 타입을 하나 만들 때마다 이렇게 물어보세요.

"이 값은 경계 반대편에서 어떻게 보이지?"

답은 그 경계를 담당하는 직렬화기(serializer)의 문서에 있어요. .NET에서 JSON 경계를 담당하는 건 System.Text.Json이에요. 이 수업에 나오는 값은 모두 문서에서 확인했고, 문서에 없는 동작은 .NET 10.0.203에서 직접 실행해서 확인했어요.

나가는 방향: C# → JSON

아래 C# 객체를 직렬화해 볼게요. 설정을 켜고 끄면서 JSON이 어떻게 바뀌는지 보세요.

C# · 직렬화할 객체public enum DiaperContent { Pee, Poo, Both }

public class DiaperRecord
{
    public Guid Id { get; init; } = Guid.NewGuid();
    public required Guid ChildId { get; init; }
    public required DateTimeOffset ChangedAt { get; set; }
    public required DiaperContent Content { get; set; }
    public string? Memo { get; set; }
}

// Content = DiaperContent.Poo, Memo = null, ChangedAt = 2026-11-04 21:30 (+09:00)

  



출력은 모두 .NET 10.0.203에서 실제로 실행한 결과예요.



토글을 다 눌러 봤다면 네 가지를 발견했을 거예요.


    
  
  1. 이름: 아무 설정도 하지 않으면 C# 이름 그대로(ChildId) 나가요. 웹 기본값은 속성 이름을 camelCase(childId)로 바꾸고, 읽을 때는 대소문자를 구분하지 않아요.[1] Microsoft 문서는 이 웹 기본값을 "ASP.NET Core가 웹 앱에 쓰는 기본 옵션"이라고 설명해요.[1] 그래서 API에서는 childId로 나가요.
    2. 
  
  2. enum: 기본은 숫자예요. Poo가 1이 돼요. 이름으로 보내려면 JsonStringEnumConverter가 필요해요.[2] 웹 기본값만 켜서는 여전히 숫자예요.
    3. 
  
  3. 날짜: DateTimeOffset은 ISO 8601 형식의 문자열로, 오프셋(+09:00)까지 포함해서 나가요.[3]
    4. 
  
  4. null: 기본적으로 모든 public 속성이 직렬화돼요.[4] 그래서 "memo": null이 나가요. WhenWritingNull을 켜면 키 자체가 사라져요.[4]
    5. 




그래서 TS 타입은 이렇게 써요


baby-log는 웹 기본값과 enum 문자열 변환을 쓰고, null은 그대로 내보낸다고 가정할게요. 이 조합에 맞는 TS 타입은 이렇습니다.




나가는 JSON{
  "id": "3f2b8c1e-…",
  "childId": "a1b2c3d4-…",
  "changedAt": "2026-11-04T21:30:00+09:00",
  "content": "Poo",
  "memo": null
}


TypeScriptconst diaperContents = ["Pee", "Poo", "Both"] as const;
type DiaperContent = (typeof diaperContents)[number];
//   ^ "Pee" | "Poo" | "Both"

type DiaperRecordDto = {
  id: string;          // Guid → string
  childId: string;
  changedAt: string;   // DateTimeOffset → string
  content: DiaperContent;
  memo: string | null; // null이 "있음"
};







값 목록과 타입은 한 곳에서 만드세요. 기저귀 입력 화면에는 "소변 / 대변 / 둘 다" 선택지가 필요해요. 그러려면 런타임에 존재하는 배열이 있어야 해요. 그런데 유니온 타입 "Pee" | "Poo" | "Both"를 따로 또 적으면, 값이 하나 추가될 때 두 곳을 고쳐야 하고 결국 언젠가 하나를 빠뜨려요. 위처럼 as const 배열을 먼저 만들고 (typeof arr)[number]로 타입을 뽑아내면 목록이 한 곳에만 있게 돼요.[7] TS 핸드북도 "요즘 TypeScript에서는 as const 객체로 충분하면 enum이 필요 없을 수 있다"고 말해요.[6]


memo?: string과 memo: string | null은 서버 설정에 따라 골라요. 서버가 null을 그대로 내보내면 키가 있고 값이 null이니 string | null을 써요. WhenWritingNull로 키를 빼면 memo?: string을 써요. 정답은 TS 쪽이 아니라 경계 반대편의 설정이 정해요.





들어오는 방향: JSON → C# (여기가 진짜 위험해요)


프론트엔드가 보낸 JSON을 C#이 읽는 방향이에요. 웹 기본값과 JsonStringEnumConverter를 켠 상태에서 여러 입력을 직접 넣어 봤어요. 오른쪽 열을 가리고 먼저 예측해 보세요.




보낸 JSON (일부)결과 (.NET 10.0.203에서 실행)



"content": "poo" (소문자)✅ 통과, Poo로 읽힘


"content": "Rainbow"❌ JsonException: could not be converted to DiaperContent


"content": 1 (숫자)✅ 통과, Poo로 읽힘


"content": 99⚠️ 통과, Content = 99(정의되지 않은 값)


content 키 없음❌ JsonException: missing required properties including: 'content'


"ChildId" (PascalCase 키)✅ 통과 (대소문자 구분 안 함)[1]


"changedAt": "…T12:30:00Z"✅ 통과, 오프셋 +00:00으로 읽힘 (같은 순간)


"changedAt": "…T21:30:00" (오프셋 없음)⚠️ 통과, 이 Mac에서는 +09:00으로 읽힘





짚어 볼 점이 세 가지 있어요.


    
  
  • required는 경계에서도 동작해요. System.Text.Json은 C#의 required를 "필수 속성"으로 취급해서, 키가 없으면 JsonException을 던져요.[5] 지난 수업에서 required를 붙인 효과가 여기까지 이어지는 거예요.
    • 
  
  • enum은 범위를 검사하지 않아요. 문자열 변환기를 켜도 숫자 입력은 여전히 받아요. 그래서 99처럼 정의되지 않은 값도 아무 오류 없이 C# 객체 안으로 들어와요. DB에 "기저귀 내용물 99"가 저장될 수 있다는 뜻이에요.
    • 
  
  • 오프셋 없는 날짜는 "코드가 실행되는 컴퓨터"의 시간대로 해석된 것으로 보여요. 이 Mac은 +09:00이라 우연히 맞았어요. 하지만 서버가 UTC로 설정된 클라우드에서 돌면 같은 입력이 9시간 어긋날 가능성이 커요. 이 부분은 실행 결과를 보고 추론한 것이고, 문서에서 직접 확인하지는 않았어요. 그래서 프론트엔드는 항상 오프셋이 붙은 시각을 보내야 해요. JS의 toISOString()은 항상 UTC(Z)로 표기해요.[8]
    • 






직렬화기는 형식만 지켜요. 의미는 지키지 않아요. JsonException을 던지는 건 "모양이 틀렸을 때"뿐이에요. "값이 말이 되는가"(enum 범위, 분유 양이 0 이하인지, 끝 시각이 시작보다 앞서는지)는 아무도 검사하지 않아요. 그래서 The Standard는 "모든 서비스는 자기 자신을 위해"(Every service for itself), 즉 각 서비스가 자기 입력과 출력을 스스로 검증해야 한다고 말해요.[10] baby-log에서는 이 검증을 Foundation 서비스의 구조적 검증에서 하게 돼요. enum 값이 정의된 값인지는 Enum.IsDefined로 확인할 수 있어요.[11]


재사용성: 직렬화 설정은 enum마다 attribute를 붙이지 말고 앱 전체에 한 번만 등록하세요. 그러면 새 enum을 추가할 때 설정을 잊을 일이 없어요.


오버엔지니어링 경계: "숫자 enum을 막는 커스텀 JsonConverter를 직접 만들자"는 생각이 들 수 있어요. 하지만 검증은 어차피 서비스 계층에서 해야 하고, 직렬화 단계에서 막아도 서비스 검증은 사라지지 않아요. 같은 규칙을 두 곳에서 지키는 셈이 되니, 지금은 서비스 검증 하나로 충분해요.





화면에 보여 줄 때: 시간대는 브라우저에서


서버는 오프셋이 붙은 시각을 그대로 보내고, 사용자에게 보여 주는 변환은 브라우저에서 해요. Intl.DateTimeFormat은 언어와 지역에 맞게 날짜를 포맷하고,[9] 따로 지정하지 않으면 그 브라우저의 기본 시간대를 써요.[9]


TypeScript: 표시용 변환은 한 곳에const timeFormat = new Intl.DateTimeFormat("ko-KR", { dateStyle: "short", timeStyle: "short" });

export const formatRecordTime = (iso: string) => timeFormat.format(new Date(iso));
// "2026-11-04T21:30:00+09:00" → 한국 브라우저: "26. 11. 4. 오후 9:30"


출력 문자열의 정확한 모양은 브라우저마다 조금씩 다를 수 있어요.



퀴즈






  
record class를 설명한 문장 중 맞는 것은?

  

    
    
    
    
  

  
타입 종류와 동등성은 서로 다른 축이에요. record class는 참조 타입이고, 컴파일러가 동등성을 값 기준으로 만들어 줘요. 이 문항이 헷갈렸다면 0002의 표를 다시 보세요.






  
ASP.NET Core API에서 Content = DiaperContent.Poo를 아무 추가 설정 없이 응답하면 JSON에는?

  

    
    
    
    
  

  
ASP.NET Core는 웹 기본값을 써서 이름은 camelCase(content)가 돼요.[1] 하지만 enum은 기본이 숫자예요.[2]






  
TS가 "content": 99를 보냈어요 (JsonStringEnumConverter 켜짐). C#에서는 어떻게 되나요?

  

    
    
    
    
  

  
실제로 실행해 보면 정의되지 않은 값 99가 그대로 들어와요. 직렬화기는 형식만 확인하니까, 의미 검증(Enum.IsDefined 등)은 서비스에서 해야 해요.[11]






  
서버가 WhenWritingNull을 쓰고 있어요. memo에 맞는 TS 타입 선언은?

  

    
    
    
    
  

  
WhenWritingNull이면 null인 속성은 키 자체가 빠져요.[4] 그래서 TS에서는 "키가 없을 수 있음", 즉 ?:로 적어요.






  
프론트엔드가 시각을 서버로 보낼 때 가장 안전한 형식은?

  

    
    
    
    
  

  
오프셋(Z 또는 +09:00)이 있어야 "어느 순간"인지 하나로 정해져요. 오프셋이 없으면 서버가 실행되는 환경의 시간대로 해석되어 어긋날 수 있어요. toISOString()이 바로 이 Z 형식을 만들어요.[8]






  
C#의 required 속성이 요청 JSON에 아예 없으면?

  

    
    
    
    
  

  
System.Text.Json은 C#의 required를 필수 속성으로 취급해서, 키가 없으면 JsonException을 던져요.[5] 컴파일 오류는 아니에요. JSON은 실행 중에 도착하니까요.






  
입력 화면의 선택지 목록과 TS 유니온 타입을 함께 관리하는 가장 좋은 방법은?

  

    
    
    
    
  

  
값 목록을 as const 배열 한 곳에만 두고, 타입은 (typeof arr)[number]로 뽑아내요.[7] 값이 추가되어도 고칠 곳이 하나뿐이에요.

이름정체네임스페이스



JsonSerializer정적 클래스. Serialize(객체 → JSON 문자열)와 Deserialize<T>(JSON 문자열 → 객체)를 제공해요[13]System.Text.Json


JsonSerializerOptions변환 규칙을 담는 객체. new로 만들어요System.Text.Json


JsonSerializerDefaultsenum(General, Web, Strict). 옵션을 만들 때 생성자에 넘기는 값이에요System.Text.Json





JsonStringEnumConverter와 JsonIgnoreCondition은 다른 네임스페이스 System.Text.Json.Serialization에 있어서 using을 하나 더 적어야 해요.


C# · 실행 가능한 전체 예제 (.NET 10.0.203에서 실행 확인)using System.Text.Json;
using System.Text.Json.Serialization;

// ① 옵션 객체를 "한 번" 만든다. 웹 기본값에서 출발해서 필요한 것만 덧붙인다
var options = new JsonSerializerOptions(JsonSerializerDefaults.Web)
{
    WriteIndented = true,                             // 사람이 읽기 좋게 줄바꿈
    Converters = { new JsonStringEnumConverter() },  // enum을 이름으로
};

var sleep = new SleepRecord
{
    ChildId = Guid.NewGuid(),
    StartedAt = DateTimeOffset.Now,
    Quality = SleepQuality.Good,
};

// ② 객체 → JSON 문자열
string json = JsonSerializer.Serialize(sleep, options);
Console.WriteLine(json);

// ③ JSON 문자열 → 객체. 타입은 <> 안에 적는다. 결과는 null일 수 있어서 SleepRecord?
SleepRecord? back = JsonSerializer.Deserialize<SleepRecord>(json, options);
Console.WriteLine(back?.Quality);

public enum SleepQuality { Good, Bad }

public class SleepRecord
{
    public required Guid ChildId { get; init; }
    public required DateTimeOffset StartedAt { get; set; }
    public DateTimeOffset? EndedAt { get; set; }
    public required SleepQuality Quality { get; set; }
}


한 줄씩 풀어 보기


    
  
  • new JsonSerializerOptions(...): 옵션은 객체라서 new로 만들어요. new를 빠뜨리면 메서드 호출로 읽혀서 CS1955 "메서드처럼 사용할 수 없다" 오류가 나요.
    • 
  
  • (JsonSerializerDefaults.Web): "웹 기본값에서 출발하라"는 뜻이에요. JsonSerializerDefaults.Web;처럼 이것만 한 줄로 쓰면 enum 값 하나만 덩그러니 놓인 셈이라 문장이 되지 않아요(CS0201). 웹 기본값은 세 가지를 바꿔요.[1]
    
      
      
    • 속성 이름을 camelCase로 써요.
      • 
      
    • 읽을 때 속성 이름의 대소문자를 구분하지 않아요.
      • 
      
    • 숫자 자리에 문자열로 된 숫자가 와도 읽어요(AllowReadingFromString).
      • 
    
    
    괄호를 비우면(new JsonSerializerOptions()) General 기본값이 돼서 "ChildId"처럼 C# 이름 그대로 나가요.
    • 
  
  • { WriteIndented = true, ... }: 객체 초기화자예요. 0002에서 new SleepRecord { ChildId = … }로 쓴 것과 같은 문법이에요.
    • 
  
  • Converters = { new JsonStringEnumConverter() }: Converters는 변환기 목록이에요. 객체를 만든 뒤에 options.Converters.Add(new JsonStringEnumConverter());로 추가해도 결과는 같아요. 단, 아래 "한 번 쓰면 잠긴다" 규칙 때문에 처음 쓰기 전에 추가해야 해요.
    • 
  
  • Serialize(sleep, options) / Deserialize<T>(json, options): 두 번째 인자로 옵션을 넘겨요. 빠뜨리면 General 기본값이 적용돼서 {"ChildId":"…","Quality":0}처럼 나가요(실행해서 확인했어요).
    • 
  
  • SleepRecord?: JSON 문자열이 null이면 Deserialize의 결과도 null이라서 반환 타입에 ?가 붙어요. 그래서 back?.Quality처럼 꺼내요.
    • 




꼭 알아 둘 규칙 두 가지


    
  
  • 옵션은 한 번 만들어서 재사용하고, 한 번 쓰면 잠겨요. Microsoft는 "같은 옵션을 반복해서 쓴다면 매번 새로 만들지 말고 같은 인스턴스를 재사용하라"고 해요. 또 "처음 직렬화하거나 역직렬화한 뒤에는 인스턴스가 변경 불가능해진다"고 해요.[1] 실제로 한 번 쓴 옵션을 바꾸려고 하면 이런 예외가 나요.

    InvalidOperationException: This JsonSerializerOptions instance is read-only
or has already been used in serialization or deserialization.
    
    .NET 9부터 있는 JsonSerializerOptions.Web도 읽기 전용이라서, 거기에 변환기를 추가하려고 하면 같은 예외가 나요(실행해서 확인했어요). 그러니 설정은 만들 때 한꺼번에 다 넣으세요.
    • 
  
  • ASP.NET Core API에서는 옵션을 직접 만들지 않아요. 프레임워크가 웹 기본값으로 만들어 두고, 우리는 거기에 설정만 덧붙여요(Controller 수업에서 다뤄요). 이 숙제는 콘솔 앱이라 직접 만드는 거예요. 자세한 설명은 질문과 답에 있어요.
    •

    ① "content":"formula" (소문자), "amountMl":120
    
    
    
    
    enum 문자열은 대소문자를 가리지 않고 읽혀요. 수업의 "들어오는 방향" 표에서 "poo"가 통과한 것과 같아요. 120ml도 범위 안이라 검증도 통과해요.
    
  
    
  
    
    
    ② "content":"Juice"
    
    
    
    
    BottleContent에 없는 이름은 변환할 수 없어서 JsonException이 나요. 검증까지 가지도 못해요.
    
  
    
  
    
    
    ③ "amountMl":"120" (숫자가 문자열로 옴)
    
    
    
    
    웹 기본값의 세 번째 항목 AllowReadingFromString 때문에 문자열 "120"도 숫자 120으로 읽혀요. 웹 기본값이 아니었다면 경계에서 막혔을 거예요.
    
  
    
  
    
    
    ④ "amountMl":-50
    
    
    
    
    -50은 형식상 올바른 정수라서 경계는 통과해요. 의미는 직렬화기가 검사하지 않으니 Validate의 1~500 범위 검사에서 막혀요. "직렬화기는 형식만, 의미는 서비스가"의 예시예요.
    
  
    
  
    
    
    ⑤ amountMl 키가 아예 없음
    
    
    
    
    AmountMl이 required라서 키가 없으면 JsonException("missing required properties")이 나요. 만약 required를 붙이지 않았다면 기본값 0이 들어가서 경계는 통과하고, 검증에서 막혔을 거예요. required 하나가 오류가 잡히는 위치를 바꿔요.
